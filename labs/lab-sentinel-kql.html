Phase 1 — Triage 5 Alerts in Splunk
Work through the morning queue using real analyst methodology
Alert 1 — Brute force: 50 failed logins, then success
Classic credential stuffing pattern
# Run in Splunk — last 24 hours
index=* (EventCode=4625 OR EventCode=4624)
| eval outcome=if(EventCode=4624,"success","failure")
| stats count(eval(outcome="failure")) as fails, count(eval(outcome="success")) as logins by src_ip, user
| where fails > 20 AND logins > 0
| sort -fails
Triage question: Is the src_ip internal or external? Is the user account a service account or human? Did the successful login happen from the same IP that failed? Write your triage note below the query results.

Alert 2 — PowerShell with encoded command
Encoded PowerShell is a common malware delivery and LOLBin technique
# Detect encoded PowerShell (Event ID 4688 or Sysmon EID 1)
index=* (EventCode=4688 OR source="WinEventLog:Microsoft-Windows-Sysmon/Operational")
| search (CommandLine="*-enc*" OR CommandLine="*-EncodedCommand*" OR CommandLine="*-e JAB*")
| table _time, ComputerName, User, CommandLine, ParentCommandLine
| sort -_time
Pivot steps: 1) Decode the Base64 payload: echo [BASE64] | base64 -d in Linux. 2) Hash the decoded script and check VirusTotal. 3) Check if the parent process makes sense (Word.exe spawning PowerShell = red flag).
Alert 3 — Impossible travel: login from 2 countries in 10 minutes
A compromised credential indicator — cannot be a real user
# Impossible travel detection — requires IP geolocation enrichment
index=* EventCode=4624 src_ip!=192.168.*
| iplocation src_ip
| stats values(Country) as countries, values(src_ip) as ips, min(_time) as first, max(_time) as last by user
| eval time_diff_min=round((last-first)/60,1)
| where mvcount(countries) > 1 AND time_diff_min < 60
| table user, countries, ips, time_diff_min
Alerts 4 + 5 — Data exfil and new admin account
Two alerts, both low-and-slow techniques
# Alert 4: Large outbound data transfer (potential exfiltration)
index=* sourcetype=firewall OR sourcetype=netflow
| stats sum(bytes_out) as total_bytes by src_ip, dest_ip
| where total_bytes > 100000000 # 100MB threshold
| eval total_mb=round(total_bytes/1048576,1)
| sort -total_mb

# Alert 5: New privileged account created outside business hours
index=* EventCode=4720 # New account created
| eval hour=strftime(_time,"%H")
| where hour < 7 OR hour > 19 # Outside 7AM–7PM
| table _time, SubjectUserName, SAMAccountName, hour

Phase 2 — Re-Run 2 Alerts in Microsoft Sentinel (KQL)
KQL fluency is the most leveraged SIEM skill in the 2026 job market
KQL equivalent of Alert 1 — Brute force in Sentinel
KQL syntax is different from SPL but the logic is the same
In Microsoft Sentinel (or aka.ms/sentineldemo) → Logs → paste this KQL:
// KQL: Brute force followed by successful login
let failedLogins = SecurityEvent
| where EventID == 4625
| summarize FailCount = count() by Account, IpAddress, bin(TimeGenerated, 5m);
let successLogins = SecurityEvent
| where EventID == 4624
| project SuccessTime = TimeGenerated, Account, IpAddress;
failedLogins
| where FailCount > 10
| join kind=inner successLogins on Account, IpAddress
| where SuccessTime > TimeGenerated
| project Account, IpAddress, FailCount, SuccessTime
| order by FailCount desc

KQL equivalent of Alert 2 — Encoded PowerShell in Sentinel
The same detection, written in KQL against the SecurityEvent table
// KQL: Encoded PowerShell execution
SecurityEvent
| where EventID == 4688
| where Process has "powershell" and (
CommandLine has "-enc" or
CommandLine has "-EncodedCommand" or
CommandLine matches regex @"-[eE][nN][cC]")
| project TimeGenerated, Computer, Account, CommandLine, ParentProcessName
| order by TimeGenerated desc
Save as Sentinel Analytics Rule: Click New alert rule → Create from query → Scheduled. Set frequency to 5 minutes, lookback 1 hour. Severity: High. This is now a production detection rule on your resume.

Phase 3 — Triage Notes & Ticket Queue
Write the notes that a real L1 analyst hands to L2 for escalation
Write triage notes for all 5 alerts
Use the standard L1 format: Who, What, When, Where, Disposition, Next Action
For each alert, document:

WHO: Account/IP involved
WHAT: What the alert fired on (event ID, rule name)
WHEN: Time range of the activity
WHERE: Source host, destination host
DISPOSITION: True Positive / False Positive / Benign True Positive / Escalate to L2
NEXT ACTION: Close / Block IP / Reset password / Escalate with context memo

SPL vs KQL side-by-side comparison
Understand the syntax differences — both appear on every SOC job description
// SPL (Splunk) KQL (Sentinel / Defender)
// --- ---
index=* EventCode=4625 SecurityEvent | where EventID == 4625
| stats count by src_ip | summarize count() by IpAddress
| where count > 5 | where count_ > 5
| sort -count | order by count_ desc
| head 10 | take 10
| eval mb=bytes/1048576 | extend mb = bytes/1048576
| table _time, src, dest | project TimeGenerated, src, dest
